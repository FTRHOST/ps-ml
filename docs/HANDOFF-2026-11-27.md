## 3. Topologi dan port

### 3.1 Jaringan yang dipakai saat ini

```text
PC      : wlan0 192.168.82.209/24, gateway 192.168.82.55
HP root : hotspot/AP 192.168.82.55
Klien   : Petwir_1 / Petwir_2 tersambung ke hotspot HP root
```

Klien hotspot **tidak bisa meng-ARP langsung IP PC** karena isolasi
client-to-client Android. Akibatnya auth bisa sukses, tetapi klien tidak pernah
membuka koneksi zone bila server mengiklankan IP PC.

Solusi: iklankan IP AP/gateway:

```bash
MODE=emulate SERVER_IP=192.168.82.209 ZONE_ADVERTISE_IP=192.168.82.55 \
  node server/index.js
```

Di log harus terlihat:

```text
Zone adv  : 192.168.82.55:30101
[AUTH:30021] Cmd_Login_CheckUpgrade_SC sConnServer=192.168.82.55:30101 ...
[ZONE:30101] klien terhubung
```

Aturan DNAT/hairpin ada di `tools/redirect.sh`:

```bash
./tools/redirect.sh status
./tools/redirect.sh wifi 192.168.82.209
```

Port yang perlu dialihkan: `30021`, `30071`, `30101`, `10003`, `30103`.

## 5. Identitas akun dan Role ID

DB menyimpan ID kecil (`1`, `2`), wire memakai offset:

```text
profileDisplayId(1) = 1000000 + 1 = 1000001  (Petwir_1)
profileDisplayId(2) = 1000000 + 2 = 1000002  (Petwir_2)
```

Inverse lookup:

```text
accountIdFromDisplay(1000001) = 1
accountIdFromDisplay(1000002) = 2
accountIdFromDisplay(1000000) = 1   (alias kompatibilitas sesi lama)
```

Env:

- `PROFILE_ID=auth` atau kosong → pakai offset (default)
- `PROFILE_ID_OFFSET=1000000` → bisa diubah
- `PROFILE_ID=12345` → mode legacy nilai mutlak (semua akun sama)

Identitas zone **per-socket**, bukan global: `sock.mlAccountId` /
`zoneAccountId`. `CURRENT_ACCOUNT` hanya dipakai fallback sebelum ada request
atau untuk logging. Ini mencegah response akun A memakai nama/level akun B.

Helper `roleIdentity(accountId)` membaca `s_name` dan `i_level` dari
`role_init_fields` setiap kali response dipatch. Variabel lama
`ACTIVE_ROLE_NAME`/`ACTIVE_LEVEL` sudah tidak dipakai untuk wire.

## 6. Cold start `-45 Session Expired`

Byte terverifikasi (12 byte):

```text
0000000c 70000201 01 15 2d 80
```

Artinya: opcode `0x70000201`, seq `1`, tag `5`, tipe neg-int, nilai `-45`.

Temuan penting:

- Build klien sekarang **tidak mengirim probe `0x1000`**; handler lama tidak
  pernah terpicu walaupun banner startup menampilkan `ColdStart: Handled`.
- Port `30071` adalah telemetri teks, bukan protokol SDP. Paket yang tidak
  cocok frame kini dicatat sebagai `[AUTH:30071] DATA TIDAK DIKENAL`.
- Solusi: `-45` dikirim sebagai **greeting segera setelah connect ke port Auth
  pertama** (`30021`), sebelum `Cmd_Login_Auth_CS`.

Log bukti:

```text
[AUTH:30021] Cold Start greeting -> tolak -45 (Session Expired) agar klien full login
[AUTH:30021] RECV 0x70000101 seq=4 ...
[AUTH] akun ditemukan: id=1 ...
```

Lompatan `seq` dari `1` ke `4` membuktikan klien mengulang login.

Env `COLDSTART_GREET=0` mematikan greeting; probe `0x1000` lama tetap menjadi
fallback.

## 7. Format capture dan replay

Sesi replay yang dipakai: `captures/2026-11-26-20-21-22/`.

- File `.zstd` = payload hasil dekompresi amplop `[10 00][u16 total][zstd]`.
- `frames.jsonl` berisi `seq`, `dir`, `port`, `opcode`, `opcode_name`,
  `envelope`, `inner_length`, waktu.
- `REPLAY_CACHE` memuat file `NNNN-s2c-<opcode>.bin|.zstd`; **sesi terbaru
  menang**, tetapi opcode lama tetap di-merge bila belum ada di sesi baru.
- Respons replay = opcode request `+ 0x100`.
- `sdp.js` adalah encoder/decoder resmi; jangan diubah.

Contoh dekode manual:

```bash
node - <<'JS'
const fs = require('fs');
const zlib = require('zlib');
const sdp = require('./sdp');
const b = fs.readFileSync('captures/2026-11-26-20-21-22/0001-c2s-70000101.zstd');
const inner = zlib.zstdDecompressSync(b);
console.log(inner.subarray(0, 16).toString('hex'));
JS
```

Capture dipakai untuk memastikan field/class:

- `Cmd_Login_Auth_CS/SC`
- `Cmd_Login_CheckUpgrade_SC`: tag `1` = `sConnServer`, tag `13` =
  `sNewConnServerList`
- `Cmd_Role_Init_SC`
- `Cmd_Role_GetInfo_SC`
- `Cmd_Account_GetAccount_SC`
- `Cmd_Battle_GetBattleData_SC`

`Cmd_Login_CheckUpgrade_SC` juga mengiklankan client version yang sama

### `Cmd_Role_Init_SC`

Semua field utama berasal dari `role_init_fields` (lihat tabel DB). `iUid` di

### `Cmd_Role_GetInfo_SC` / `PlayerBaseInfo`

| Tag | Field | Nilai sekarang |
|---|---|---|
| 0 | `ulUid` | `profileDisplayId(accountId)` |
| 1 | `uiSvrId` | `9218` (Zone/Server ID, lihat bawah) |
| 2 | `sName` | `roleIdentity(accountId).name` |
| 3 | `uiLevel` | `roleIdentity(accountId).level` |
| 6 | `uiRankLevel` | dari capture / Role_Init |
| 9 | `uiHeroNum` | `COUNT(*)` `cmd_hero_data` akun → `135` |
| 10 | `uiHeroSkinNum` | `COUNT(*)` `cmd_hero_skin` akun → `1` |
| 11 | `uiPVPRank` | dari capture (`2855`) |
| 13 | `iFaceBorderId` | dari capture (`127`) |

Angka `121` dan `181` yang dulu terlihat di profil adalah nilai capture lama
untuk `uiHeroNum`/`uiHeroSkinNum`, sekarang tidak dipakai.

Request-nya `Cmd_Role_GetBaseInfo_CS` (`0x70009f4f`) membawa **uid akun tujuan**
pada struct tag `0` dan svrId `9218` pada tag `1` (terverifikasi dari
`captures/2026-11-26-20-21-22/1859-c2s-70009f4f.bin`: `332108113`, `9218`).
`resolveProfileTargetAccountId()` mengubah uid tampilan (`1000000 + id DB`)
kembali jadi id DB, lalu patch memakai identitas akun tujuan. Fallback ke akun
socket dipakai bila uid bukan akun lokal (mis. uid server resmi dari capture).
Dengan ini klik info teman menampilkan profil teman, bukan profil viewer.

### `Cmd_Account_GetAccount_SC`

- tag `0` = `iAccountId` (bukan uid role) → `1000001`/`1000002`
- list tag `2`: tiap item uid di tag `1`, nama di tag `2`, keduanya per-akun

### `Cmd_Battle_GetBattleData_SC`

Request `Cmd_Battle_GetBattleData_CS` (`0x7000d694`) juga membawa uid tujuan di
struct tag `0` dan svrId di tag `1` (sama dengan request profil), sehingga
`currentRoleProfile()` kini memakai akun tujuan, bukan viewer.

- tag `17` = `ulUid`
- tag `18` = `uiSvrId` (`9218`)
- struct tag `19` → field `0` uid, `1` svrId, `2` name, `3` level, `4` faceId

### `Cmd_Friend_RecommendFriend_SC` (`0x7000a557`)

Balasan dari request `0x7000a457` saat panel Add Friends dibuka. Request-nya
**tidak punya field aplikasi** (`Cmd_Friend_RecommendFriend_CS` kosong di
`dump.cs`); isi 16 byte hanya header: panjang, opcode, seq, message ID, penanda
arah `0x45`, string placeholder `70 80`, dan StructEnd.

Response sekarang dibangun ulang dari DB:

- tag `0` `vecFriends`: satu `FriendBaseInfo` per akun DB selain akun yang
  sedang login (maksimal 6);
- tag `1` `iForceRecomNum`: jumlah kandidat dari DB;
- tiap `FriendBaseInfo` memakai tag `0` uid, `1` svrId `9218`, `2` nama,
  `3` level, `4` faceId, `5` lastLoginTime dari DB,
  `8` rankLevel, `9` pvpRank, `13` client version `2.2.30.1235.1`,
  `14` faceBorderId, `15` nationality, dan `16` face path kosong.
  Tag `6` (`uiStatus`) **sengaja dihapus**, mengikuti entri offline di capture
  asli: kehadiran field status membuat klien melabeli "Online" walaupun
  nilainya `0`. Dengan tag `6` absen, klien menampilkan "terakhir kali login"
  dari tag `5`. Field lain (tim, dll) tetap memakai template capture.

### `9218` itu apa?

`9218` adalah **Zone ID / Server ID** (`ROLE_SVR_ID`), sumbernya
`state/role.json` (`zoneId`/`serverId`) atau env `ROLE_SVR_ID`. Bukan account ID
dan bukan UID role. Sengaja sama untuk `Petwir_1` dan `Petwir_2` karena keduanya
dianggap berada di zona yang sama.

## 11. Status dan blocker

### Sudah terverifikasi

- `Petwir_1` dan `Petwir_2` login ke server lokal serta masuk lobby.
- greeting `-45` memicu full login; telemetri klien menampilkan `1000001`.
- Koneksi zone `Petwir_2` berhasil setelah `ZONE_ADVERTISE_IP=192.168.82.55`.

- Panel Add Friends mengambil rekomendasi dari DB: akun `1` melihat `Petwir_2`,
  akun `2` melihat `Petwir_1`, dan diri sendiri tidak ikut dalam daftar.
- Klik info player dari rekomendasi menampilkan profil akun tujuan (uid di request),
  bukan profil viewer.
- `node test-sdp.js` → `7 lulus, 0 gagal`.
- Git bersih, semua commit sudah di-push ke `origin/main`.

### Blocker saat ini

- `adb devices -l` kosong dan `frida-server` tidak jalan, sehingga
  `./tools/redirect.sh status` tidak bisa dijalankan dari PC. DNAT/hairpin di HP
  root tidak bisa dicek/dipasang otomatis. Jika zone gagal lagi, sambungkan
  device/Frida lalu jalankan ulang `./tools/redirect.sh wifi 192.168.82.209`.
- `state/game.db` sengaja tidak di-commit. Clone baru akan membuat DB dengan
  default saat server pertama kali jalan.
- Saat panel Add Friends dibuka muncul pula `cache miss 0x7000cb5e -> 0x7000cc5e`
  dan frame tercatat di `unhandled/`. Fungsi opcode ini belum diidentifikasi
  (kemungkinan fitur pencarian/undangan tambahan), tetapi tidak menghalangi
  daftar rekomendasi.

### Belum diimplementasikan

- Zone ID per-akun: `9218` masih global. Bila tiap akun perlu zona berbeda,
  tambahkan kolom `i_zone_id` ke `role_init_fields`, lalu pakai
  `roleIdentity(accountId).zoneId`.
- Field battle profile `faceId`, `nationality`, `rankLevel`, `faceBorderId`
  masih memakai nilai global `state/role.json` di `currentRoleProfile()`;
  field yang sudah per-akun adalah yang dikirim lewat `Cmd_Role_Init_SC`.
- Beberapa opcode masih `cache miss`/tidak tertangani (`unhandled/`). Rekam
  ulang via relay bila perlu menambah cache.

### Saran langkah berikutnya

1. Uji dua akun bersamaan di dua perangkat dan pastikan log tetap konsisten.
2. Jika pindah jaringan, cek gateway lalu set `ZONE_ADVERTISE_IP` ke IP AP.
3. Pindahkan sisa field global battle profile ke DB bila dibutuhkan.
4. Perbanyak cache opcode dari sesi capture baru; jangan menyentuh `sdp.js`.
5. Selalu jalankan gate `node test-sdp.js` sebelum commit.
