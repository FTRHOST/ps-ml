## 3. Topologi dan port

### 3.1 Jaringan yang dipakai saat ini

```text
PC      : wlan0 192.168.82.209/24, gateway 192.168.82.55
HP root : hotspot/AP 192.168.82.55
Klien   : Petwir_1 / Petwir_2 tersambung ke hotspot HP root
```

Klien hotspot **tidak bisa meng-ARP langsung IP PC** karena isolasi
client-to-client Android. Akibatnya auth bisa sukses, tetapi klien tidak pernah
membuka koneksi zone bila server mengiklankan IP PC.

Solusi: iklankan IP AP/gateway:

```bash
MODE=emulate SERVER_IP=192.168.82.209 ZONE_ADVERTISE_IP=192.168.82.55 \
  node server/index.js
```

Di log harus terlihat:

```text
Zone adv  : 192.168.82.55:30101
[AUTH:30021] Cmd_Login_CheckUpgrade_SC sConnServer=192.168.82.55:30101 ...
[ZONE:30101] klien terhubung
```

Aturan DNAT/hairpin ada di `tools/redirect.sh`:

```bash
./tools/redirect.sh status
./tools/redirect.sh wifi 192.168.82.209
```

Port TCP yang perlu dialihkan: `30021`, `30071`, `30101`, `10003`, `30103`.
Port UDP ping yang ikut dialihkan: `30101`, `10003`, `30103`, `7000`, `8000`,
`9000`.

### 3.2 Peran port

| Port | Peran | Catatan |
|---|---|---|
| `30021` | Auth protokol SDP | greeting `-45`, `0x70000101` Auth_CS, `0x70000501` CheckUpgrade, `0x70000701` GetBulletin |
| `30071` | Telemetri teks | `client_loginv2_data`, `unity2017_launch_log`, `error_data_report`. **Jangan kirim frame SDP ke sini** |
| `30101` | Zone utama | handshake `0x7000914e`, Role_Init, GetInfo, GetAccount, Hero_GetList, dll |
| `10003`, `30103` | Zone tambahan | dipakai sebagian build/capture |

### 3.3 Ping lokal

Ping tidak lagi memakai IP Softlayer dari capture.

| Bagian | Perlakuan |
|---|---|
| `Cmd_Ping_GetAllServerIp_SC` (`0x7000d195`) | semua `vIpList` diganti ke `PING_LOCAL_IP`; `sMd5` dihitung ulang |
| `Cmd_Act_CityPing_GetPing_SC` (`0x7000f9ff`) | angka capture `18`/`156` diganti `PING_LOCAL_MS` |
| UDP | listener echo di `PING_UDP_PORTS`, datagram dikirim balik apa adanya |
| TCP `Cmd_Net_Echo_CS` (`0x7000954e` → `0x7000964e`) | balasan ditunda `PING_TCP_ECHO_DELAY_MS` ms; **ini yang dipakai angka ping lobby** |
| `tools/redirect.sh wifi` | DNAT + MASQUERADE UDP ditambahkan di `OUTPUT`, `PREROUTING`, `POSTROUTING` |

Default:

```text
PING_LOCAL_IP           = PING_SERVER_IP || ZONE_ADVERTISE_IP || SERVER_IP || HOST
PING_UDP_PORT           = 30101,10003,30103,7000,8000,9000
PING_LOCAL_MS           = 1
PING_ECHO_DELAY_MS      = 0 (echo UDP langsung; tidak memengaruhi angka lobby)
PING_TCP_ECHO_DELAY_MS  = 200 (RTT lobby terukur ~200 ms; alias: DELAY)
```

Mode `on` (adb reverse) sekarang juga memasang DNAT UDP ke IP PC, jadi ping
lokal bekerja di jalur USB maupun wifi:

```bash
MODE=emulate SERVER_IP=192.168.82.209 ZONE_ADVERTISE_IP=192.168.82.55 \
  node server/index.js
./tools/redirect.sh on 192.168.82.209    # adb forward + DNAT UDP
# atau
./tools/redirect.sh wifi 192.168.82.209  # LAN/hotspot saja
```

`PING_TCP_ECHO_DELAY_MS` menunda balasan `Cmd_Net_Echo_SC`, sehingga klien
mengukur RTT secara nyata (~200 ms) dan menampilkannya di lobby. Ini bukan
angka statis yang ditulis ke packet: request dan response benar-benar melewati
jaringan lokal, hanya server yang menahan respons. Set `0` bila ingin angka
lobby mengikuti latensi lokal sebenarnya (~16 ms atau lebih rendah).
`DELAY=0` adalah alias yang sama dengan `PING_TCP_ECHO_DELAY_MS=0`.

Catatan uji:

- `PING_ECHO_DELAY_MS=200` membuat RTT UDP lokal ~201 ms, tetapi angka lobby
  tetap ~16 ms. Jadi echo UDP **bukan** sumber angka UI lobby.
- `PING_TCP_ECHO_DELAY_MS=200` membuat angka lobby ~200 ms. Log server:
  `tunda 0x7000964e 200ms (RTT ping lobby)`, dan probe lokal terukur
  `201–205 ms`.

Frida/Il2Cpp juga menunjukkan `NetUtil.PingManager` mengirim UDP ping aktif,
tetapi jalur UI lobby memakai RTT echo TCP; hook `ViewPingFPS.UpdatePing` dan
`CTools2Wrap.GetPingValue` tidak dipanggil pada build ini.

Verifikasi cepat dari HP:

```bash
adb shell "printf PINGTEST | toybox nc -u -w 2 192.168.82.55 7000"
# balasan: PINGTEST
```

Di log server harus ada:

```text
[PING:UDP:7000] 192.168.82.55:<port> 8B echo hex=50494e4754455354
[ZONE:30101] patch Cmd_Ping_GetAllServerIp_SC -> 192.168.82.55 (2043 ip, 295 grup, ...)
```

Klien menyimpan daftar IP di cache, jadi **restart game** diperlukan setelah
pertama kali patch diterapkan agar daftar IP baru diambil. Hasil uji lapangan:
ping turun dari ~200 ms → ~113 ms → ~16 ms, dengan nilai sesekali ~7 ms dan
spike saat jaringan/HP sibuk.

### 3.4 Mode VPS + hotspot HP root

Server bisa dijalankan di VPS; HP root berperan sebagai klien **dan** router
DNAT. Tidak perlu memakai IP AP/gateway seperti topologi LAN di 3.1: iklankan
langsung IP publik VPS.

Di VPS:

```bash
SERVER_IP=<IP_PUBLIK_VPS> ZONE_ADVERTISE_IP=<IP_PUBLIK_VPS> DELAY=0 \
  node server/index.js
```

`HOST` tetap `0.0.0.0` (default), jadi tidak perlu diubah. Firewall VPS **dan** security group provider harus membuka. Di VPS jalankan:

```bash
./tools/vps-firewall.sh
# bila SSH bukan port 22:
SSH_PORT=2222 ./tools/vps-firewall.sh
```

Skrip itu mengizinkan port SSH lebih dulu, membuka TCP
`30021/30071/30101/10003/30103` dan UDP `30101/10003/30103/7000/8000/9000`,
lalu mengaktifkan ufw dengan `--force enable` tanpa prompt. Port security group
provider tetap harus dibuka manual karena tidak bisa diatur dari ufw.

Di HP root (tetap lewat `adb` + `frida-server`, karena aturan dipasang root):

```bash
./tools/redirect.sh vps <IP_PUBLIK_VPS>
./tools/redirect.sh status
```

Alternatif yang konfigurasinya disimpan **di dalam script**:

```bash
# edit VPS_IP di blok KONFIGURASI tools/device-vps.sh
./tools/device-vps.sh            # pasang
./tools/device-vps.sh status
./tools/device-vps.sh off
```

`device-vps.sh` tetap dieksekusi dari PC, lalu mengirim perintah iptables ke HP
sebagai root lewat `tools/rootcmd.py` (frida-server). Blok `KONFIGURASI` memuat
`VPS_IP`, daftar port TCP/UDP, interface hotspot/uplink, dan opsi hotspot.
Nilai env seperti `VPS_IP=203.0.113.10 ./tools/device-vps.sh` juga dipakai bila
diisi.

Mode `vps` / `device-vps.sh` memasang:

- `OUTPUT` DNAT TCP/UDP untuk game yang berjalan di HP itu sendiri;
- `PREROUTING` DNAT TCP/UDP untuk klien yang masuk lewat `ap0` (hotspot);
- `POSTROUTING` MASQUERADE di uplink (`wlan0`/`rmnet`) agar balasan VPS kembali
  ke HP, lalu diteruskan ke klien hotspot lewat conntrack.

Jalurnya: `klien hotspot -> ap0 -> DNAT ke VPS -> uplink -> VPS -> balasan ->
MASQUERADE -> conntrack -> klien`. Karena tujuan bukan PC di `ap0` yang sama,
tidak ada hairpin `ap0 -> ap0`, jadi aturan `tetherctrl_FORWARD` tambahan tidak
dipasang.

Catatan penting:

- Jangan mengisi `ZONE_ADVERTISE_IP` dengan IP privat VPS (`10.x`,
  `172.16–31.x`, `192.168.x`); klien di internet tidak bisa merutekannya.
- `PING_LOCAL_IP` otomatis mengikuti `ZONE_ADVERTISE_IP`, jadi daftar IP ping
  juga berisi IP VPS.
- Mode `vps` menggantikan `wifi`/`on` bila server tidak lagi di PC.
- Aturan iptables hilang setelah reboot HP; jalankan ulang `./tools/redirect.sh
  vps <IP_PUBLIK_VPS>` atau `./tools/device-vps.sh`.

## 5. Identitas akun dan Role ID

DB menyimpan ID kecil (`1`, `2`), wire memakai offset:

```text
profileDisplayId(1) = 1000000 + 1 = 1000001  (Petwir_1)
profileDisplayId(2) = 1000000 + 2 = 1000002  (Petwir_2)
```

Inverse lookup:

```text
accountIdFromDisplay(1000001) = 1
accountIdFromDisplay(1000002) = 2
accountIdFromDisplay(1000000) = 1   (alias kompatibilitas sesi lama)
```

Env:

- `PROFILE_ID=auth` atau kosong → pakai offset (default)
- `PROFILE_ID_OFFSET=1000000` → bisa diubah
- `PROFILE_ID=12345` → mode legacy nilai mutlak (semua akun sama)

Identitas zone **per-socket**, bukan global: `sock.mlAccountId` /
`zoneAccountId`. `CURRENT_ACCOUNT` hanya dipakai fallback sebelum ada request
atau untuk logging. Ini mencegah response akun A memakai nama/level akun B.

Helper `roleIdentity(accountId)` membaca `s_name` dan `i_level` dari
`role_init_fields` setiap kali response dipatch. Variabel lama
`ACTIVE_ROLE_NAME`/`ACTIVE_LEVEL` sudah tidak dipakai untuk wire.

## 6. Cold start `-45 Session Expired`

Byte terverifikasi (12 byte):

```text
0000000c 70000201 01 15 2d 80
```

Artinya: opcode `0x70000201`, seq `1`, tag `5`, tipe neg-int, nilai `-45`.

Temuan penting:

- Build klien sekarang **tidak mengirim probe `0x1000`**; handler lama tidak
  pernah terpicu walaupun banner startup menampilkan `ColdStart: Handled`.
- Port `30071` adalah telemetri teks, bukan protokol SDP. Paket yang tidak
  cocok frame kini dicatat sebagai `[AUTH:30071] DATA TIDAK DIKENAL`.
- Solusi: `-45` dikirim sebagai **greeting segera setelah connect ke port Auth
  pertama** (`30021`), sebelum `Cmd_Login_Auth_CS`.

Log bukti:

```text
[AUTH:30021] Cold Start greeting -> tolak -45 (Session Expired) agar klien full login
[AUTH:30021] RECV 0x70000101 seq=4 ...
[AUTH] akun ditemukan: id=1 ...
```

Lompatan `seq` dari `1` ke `4` membuktikan klien mengulang login.

Jalur probe `0x1000` lama sekarang hanya **dicatat dan diabaikan**, tidak
mengirim `-45` lagi. Greeting saat connect tetap menjadi satu-satunya pengirim `-45`
supaya tidak ada penolakan ganda bila klien tertentu tetap mengirim probe.

Env `COLDSTART_GREET=0` sekarang benar-benar mematikan `-45` (greeting mati dan
probe diabaikan). Default tetap `COLDSTART_GREET=1` karena build klien ini tidak
mengirim `0x1000`, sehingga `-45` harus diinisiasi server supaya sesi lama di
cache dibuang dan klien melakukan full login.

## 7. Format capture dan replay

Sesi replay yang dipakai: `captures/2026-11-26-20-21-22/`.

- File `.zstd` = payload hasil dekompresi amplop `[10 00][u16 total][zstd]`.
- `frames.jsonl` berisi `seq`, `dir`, `port`, `opcode`, `opcode_name`,
  `envelope`, `inner_length`, waktu.
- `REPLAY_CACHE` memuat file `NNNN-s2c-<opcode>.bin|.zstd`; **sesi terbaru
  menang**, tetapi opcode lama tetap di-merge bila belum ada di sesi baru.
- Respons replay = opcode request `+ 0x100`.
- `sdp.js` adalah encoder/decoder resmi; jangan diubah.

Contoh dekode manual:

```bash
node - <<'JS'
const fs = require('fs');
const zlib = require('zlib');
const sdp = require('./sdp');
const b = fs.readFileSync('captures/2026-11-26-20-21-22/0001-c2s-70000101.zstd');
const inner = zlib.zstdDecompressSync(b);
console.log(inner.subarray(0, 16).toString('hex'));
JS
```

Capture dipakai untuk memastikan field/class:

- `Cmd_Login_Auth_CS/SC`
- `Cmd_Login_CheckUpgrade_SC`: tag `1` = `sConnServer`, tag `13` =
  `sNewConnServerList`
- `Cmd_Role_Init_SC`
- `Cmd_Role_GetInfo_SC`
- `Cmd_Account_GetAccount_SC`
- `Cmd_Battle_GetBattleData_SC`

Keduanya sekarang dibangun ulang dari `state/game.db` dan akun viewer
disingkirkan. `patchSquadInfoBody()` mengganti uid/zone/level anggota di tag
`20` serta uid leader (tag `7`/`41`), sedangkan `patchFriendListBody()` dipakai
ulang untuk `0x7000fcb8` supaya nama, level, dan field identitas lainnya mengikuti DB.
Hasilnya: `Petwir_1` hanya melihat `Petwir_2` sebagai member, dan sebaliknya.

Binding viewer juga diperbaiki: `resolveRequestAccountId()` tidak lagi menyimpan
fallback `CURRENT_ACCOUNT`/`getLastAccountId()` ke socket sebelum Role_Init.
Flag `sock.mlAccountBound` hanya aktif setelah `sAccountName` request dikenali
atau `Cmd_Role_Init_SC` diproses. Sebelum itu, semua patch daftar mengirim list
kosong agar identitas stale tidak pernah tampil sebagai "diri sendiri".

### `Cmd_Account_GetAccount_SC`

- tag `0` = `iAccountId` (bukan uid role) → `1000001`/`1000002`
- list tag `2`: tiap item uid di tag `1`, nama di tag `2`, keduanya per-akun

### `Cmd_Battle_GetBattleData_SC`

Request `Cmd_Battle_GetBattleData_CS` (`0x7000d694`) juga membawa uid tujuan di
struct tag `0` dan svrId di tag `1` (sama dengan request profil), sehingga
`currentRoleProfile()` kini memakai akun tujuan, bukan viewer.

- tag `17` = `ulUid`
- tag `18` = `uiSvrId` (`9218`)
- struct tag `19` → field `0` uid, `1` svrId, `2` name, `3` level, `4` faceId

### `Cmd_Friend_RecommendFriend_SC` (`0x7000a557`)

Balasan dari request `0x7000a457` saat panel Add Friends dibuka. Request-nya
**tidak punya field aplikasi** (`Cmd_Friend_RecommendFriend_CS` kosong di
`dump.cs`); isi 16 byte hanya header: panjang, opcode, seq, message ID, penanda
arah `0x45`, string placeholder `70 80`, dan StructEnd.

Response sekarang dibangun ulang dari DB:

- tag `0` `vecFriends`: satu `FriendBaseInfo` per akun DB selain akun yang
  sedang login (maksimal 6);
- tag `1` `iForceRecomNum`: jumlah kandidat dari DB;
- tiap `FriendBaseInfo` memakai tag `0` uid, `1` svrId `9218`, `2` nama,
  `3` level, `4` faceId, `5` lastLoginTime dari DB,
  `8` rankLevel, `9` pvpRank, `13` client version `2.2.30.1235.1`,
  `14` faceBorderId, `15` nationality, dan `16` face path kosong.
  Tag `6` (`uiStatus`) **sengaja dihapus**, mengikuti entri offline di capture
  asli: kehadiran field status membuat klien melabeli "Online" walaupun
  nilainya `0`. Dengan tag `6` absen, klien menampilkan "terakhir kali login"
  dari tag `5`. Field lain (tim, dll) tetap memakai template capture.

### `9218` itu apa?

`9218` adalah **Zone ID / Server ID** (`ROLE_SVR_ID`), sumbernya
`state/role.json` (`zoneId`/`serverId`) atau env `ROLE_SVR_ID`. Bukan account ID
dan bukan UID role. Sengaja sama untuk `Petwir_1` dan `Petwir_2` karena keduanya
dianggap berada di zona yang sama.

## 11. Status dan blocker

### Sudah terverifikasi

- `Petwir_1` dan `Petwir_2` login ke server lokal serta masuk lobby.
- greeting `-45` memicu full login; telemetri klien menampilkan `1000001`.
- Koneksi zone `Petwir_2` berhasil setelah `ZONE_ADVERTISE_IP=192.168.82.55`.
- Nama, level, dan jumlah hero/skin per-akun sesuai DB.
- Panel Add Friends mengambil rekomendasi dari DB: akun `1` melihat `Petwir_2`,
  akun `2` melihat `Petwir_1`, dan diri sendiri tidak ikut dalam daftar.
- Klik info player dari rekomendasi menampilkan profil akun tujuan (uid di request),
  bukan profil viewer.
- Friend list dan visitor profil hanya memuat akun DB; `Lafaaa FT support`
  tidak muncul lagi.
- Sidebar/member squad `POTM` tidak lagi menampilkan akun yang sedang login,
  untuk `Petwir_1` maupun `Petwir_2`.
- Ping lokal: daftar IP capture diganti, UDP echo + DNAT terverifikasi dari HP,
  dan sumber angka lobby ditemukan pada RTT `Cmd_Net_Echo_CS/SC`. Dengan delay
  default 200 ms, ping lobby stabil ~200 ms; set `PING_TCP_ECHO_DELAY_MS=0`
  untuk kembali ke latensi lokal ~16 ms.
- `node test-sdp.js` → `7 lulus, 0 gagal`.
- Git bersih, semua commit sudah di-push ke `origin/main`.

### Blocker saat ini

- `state/game.db` sengaja tidak di-commit. Clone baru akan membuat DB dengan
  default saat server pertama kali jalan.
- Saat panel Add Friends dibuka muncul pula `cache miss 0x7000cb5e -> 0x7000cc5e`
  dan frame tercatat di `unhandled/`. Fungsi opcode ini belum diidentifikasi
  (kemungkinan fitur pencarian/undangan tambahan), tetapi tidak menghalangi
  daftar rekomendasi.

### Belum diimplementasikan

- Zone ID per-akun: `9218` masih global. Bila tiap akun perlu zona berbeda,
  tambahkan kolom `i_zone_id` ke `role_init_fields`, lalu pakai
  `roleIdentity(accountId).zoneId`.
- Field battle profile `faceId`, `nationality`, `rankLevel`, `faceBorderId`
  masih memakai nilai global `state/role.json` di `currentRoleProfile()`;
  field yang sudah per-akun adalah yang dikirim lewat `Cmd_Role_Init_SC`.
- Beberapa opcode masih `cache miss`/tidak tertangani (`unhandled/`). Rekam
  ulang via relay bila perlu menambah cache.

### Saran langkah berikutnya

1. Uji dua akun bersamaan di dua perangkat dan pastikan log tetap konsisten.
2. Jika pindah jaringan, cek gateway lalu set `ZONE_ADVERTISE_IP` ke IP AP.
3. Pindahkan sisa field global battle profile ke DB bila dibutuhkan.
4. Perbanyak cache opcode dari sesi capture baru; jangan menyentuh `sdp.js`.
5. Selalu jalankan gate `node test-sdp.js` sebelum commit.
